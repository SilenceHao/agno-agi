# 企业级智能体知识库权限隔离改造提示词

## 一、改造目标

请基于当前 Agno 智能体项目，对知识库权限隔离机制进行专项分析和改造。

当前系统已经实现基于 RBAC 的知识库目录授权：

- 用户可以绑定多个角色。
- 每个角色可以被授权访问一个或多个知识库目录。
- 用户最终可访问的知识库目录范围为其所有角色授权目录的并集。
- 超级管理员可以访问全部知识库。
- 普通用户只能访问自己获得授权的知识库内容。

目前存在的问题：

1. 用户已经获得知识库授权，但提问时偶尔提示没有权限。
2. 不同知识库之间偶尔出现检索结果串库。
3. 当前通过全库召回、服务端拆分授权与未授权结果、比较最佳向量距离来判断是否允许回答，容易造成误判。
4. 需要确保任何未授权知识内容都不会进入大模型上下文。

本次改造必须以现有业务和代码结构为基础，优先最小侵入式改造，不要无理由重构整个 RAG 系统。

## 二、核心架构原则

采用：

**RBAC + 资源级授权 + 检索前强制过滤 + 检索结果二次权限校验。**

必须严格区分两个概念：

1. 权限控制：用户是否有权访问某个知识库。
2. 相关性检索：用户有权访问的知识库中，哪些内容与问题最相关。

禁止使用向量距离、相似度分数、TopK 排名来判断用户是否有权访问知识库。

向量相似度只能用于相关性排序，不能作为权限判断依据。

## 三、正确的权限计算逻辑

### 3.1 用户身份解析

每次知识库问答请求，都必须从服务端可信的身份认证信息中获取：

- userId
- tenantId
- 用户角色列表
- 当前 agentId

不能信任前端直接传入的角色 ID、知识库 ID 或目录 ID 作为授权依据。

### 3.2 获取授权目录集合

普通用户：

1. 查询用户绑定的全部角色。
2. 查询所有角色获得的知识库目录授权。
3. 将多个角色的授权目录合并去重。
4. 得到用户最终授权目录集合。

超级管理员：

- 按现有业务规则绕过目录权限限制。
- 仍然必须遵守适用的企业租户隔离规则。

没有角色或没有任何知识库授权时，授权范围为空。

### 3.3 计算实际可检索知识库范围

根据授权目录集合，结合当前智能体关联的知识库，计算本次请求真正允许检索的资源范围。

必须保证：

- 只能检索当前智能体关联的知识库。
- 只能检索当前用户授权目录范围内的文档。
- 父目录授权时，按照现有目录继承规则包含合法的子目录。
- 多角色授权采用并集。
- 未授权目录不能进入检索候选范围。
- 空授权集合不能退化为全库检索。

如果一个知识库同时包含授权和未授权目录，只允许检索授权目录中的文档，不得直接放开整个知识库。

## 四、核心改造：检索前权限过滤

这是本次改造最重要的部分。

### 4.1 删除当前错误的检索判断机制

移除以下逻辑：

1. 先从全库检索 KNOWLEDGE_SEARCH_RESULTS * 3 条候选。
2. 服务端再将候选拆分为授权和未授权结果。
3. 分别计算最佳向量距离。
4. 比较最佳授权与未授权结果的距离。
5. 当未授权结果更相关时，清空授权结果。
6. 因为未授权结果更相关而返回无权限提示。

不再允许未授权知识库参与普通用户的召回竞争。

### 4.2 建立统一的授权过滤条件

检索之前，必须构建服务端生成的检索过滤条件。

建议包含：

- tenant_id
- knowledge_base_id
- directory_id
- document_status
- 其他现有的数据有效性条件

具体字段应以当前项目实际数据结构为准。

过滤条件必须由后端权限服务生成，不能由大模型生成，也不能由前端指定。

### 4.3 向量检索

执行向量检索时，直接在向量数据库层面注入授权过滤条件。

例如：

用户授权目录：

[101, 102, 103]

则本次向量检索只能召回这些目录及其合法继承范围内的文档。

禁止：

- 全库检索后再过滤。
- 先检索再依赖大模型识别权限。
- 授权范围为空时不传过滤条件。
- 过滤失败时自动降级成全库检索。

如果底层向量数据库不支持当前所需的过滤条件，必须在服务端采用可靠的等价约束方式实现，不能牺牲权限安全。

### 4.4 混合检索

如果系统同时存在：

- 向量检索
- BM25
- 全文检索
- 关键词检索
- Rerank

所有召回路径必须使用完全一致的授权范围。

不能只有向量检索执行权限过滤，而关键词检索仍然从全库召回。

Rerank 只能处理已经通过权限过滤的候选内容。

### 4.5 TopK 处理

KNOWLEDGE_SEARCH_RESULTS 应作用于授权范围内的检索结果。

不能先从全库取 TopK，再过滤出少量授权结果。

如果授权范围内没有相关结果，按照正常无相关资料处理。

## 五、检索结果二次权限校验

即使检索阶段已经过滤，也必须进行第二次校验。

对每个召回的 Chunk 检查：

1. tenant_id 是否匹配当前请求。
2. knowledge_base_id 是否属于当前智能体。
3. directory_id 是否在当前用户有效授权范围内。
4. document_id 是否仍然有效。
5. 文档是否已删除、下架或失效。

任何一项校验失败：

- 禁止该 Chunk 进入模型上下文。
- 记录安全审计日志。
- 必要时直接阻断本次模型调用。

禁止仅依靠向量数据库返回的结果就直接构建 LLM 上下文。

## 六、模型上下文隔离

必须确保只有通过权限校验的知识分片才能进入大模型。

需要检查：

1. RAG 检索结果。
2. 对话历史。
3. 历史知识库引用。
4. 缓存的检索结果。
5. Agent 工具调用结果。
6. 子 Agent 的检索结果。
7. 工作流中的知识库节点。

特别注意历史对话：

如果用户之前有权访问某个知识库，之后权限被撤销，不能因为继续使用旧对话就继续使用之前检索到的未授权知识内容。

建议为检索引用保存：

- knowledge_base_id
- directory_id
- document_id
- permission_version 或相关授权版本信息

在权限变化后，对历史引用重新校验，必要时重新构建上下文。

## 七、无权限与无相关内容必须严格区分

统一区分以下情况：

### 情况 A：没有任何知识库授权

普通用户没有任何可访问的知识库。

按照产品策略提示：

「当前账号尚未获得知识库访问权限，请联系管理员分配权限。」

### 情况 B：拥有知识库权限，但没有检索到相关内容

正常返回：

「在当前可访问的知识库中，没有找到与问题相关的资料。」

不能提示用户没有权限。

### 情况 C：拥有知识库权限，且检索到相关内容

正常进入模型回答流程。

### 情况 D：检索服务异常

返回检索服务异常，不得错误地解释为用户没有权限。

### 情况 E：检索结果二次校验失败

阻止不合规内容进入模型，记录安全日志，并按照安全策略处理本次请求。

禁止把未授权知识库是否存在相关内容、文档名称、内容摘要等信息透露给普通用户。

## 八、缓存权限隔离

检查所有 RAG 相关缓存：

- Embedding 缓存
- 检索结果缓存
- 语义缓存
- Agent 回答缓存

缓存 Key 至少要考虑：

- tenantId
- agentId
- 用户有效授权范围或其稳定哈希
- permissionVersion
- 查询内容哈希
- 相关检索配置版本

缓存命中后也必须执行必要的权限校验。

权限发生变化时，旧权限范围下的缓存不能直接复用。

不能仅使用 question 作为缓存 Key。

## 九、统一权限服务

建议将权限逻辑独立封装，避免 chat() 内部重复实现权限判断。

可以根据现有代码结构设计以下接口：

```python
get_user_resource_scope(user_id, agent_id)

get_authorized_knowledge_directories(user_id, agent_id)

build_knowledge_retrieval_filter(
    user_id,
    agent_id,
    tenant_id
)

validate_retrieval_results(
    documents,
    authorized_scope
)
```

具体函数名称和参数允许根据项目实际结构调整。

核心要求：

所有知识库检索入口必须使用统一的权限计算服务。

不能只保护 chat() 主流程而遗漏：

- Agent 工具调用
- 子 Agent
- 工作流节点
- 独立知识库查询接口
- HTTP 工具
- 其他 RAG 调用入口

## 十、专项日志与排查能力

每次检索增加结构化诊断日志：

```json
{
  "user_id": "10001",
  "agent_id": "20001",
  "tenant_id": "company_001",
  "role_ids": [1, 2],
  "authorized_directory_ids": [101, 102],
  "authorized_knowledge_base_ids": [10],
  "retrieved_knowledge_base_ids": [10],
  "retrieved_chunk_count": 5,
  "unauthorized_chunk_count": 0,
  "permission_version": 12
}
```

重点记录：

- 授权范围。
- 实际检索范围。
- 召回结果所属知识库。
- 二次权限校验结果。
- 是否发生越权召回。
- 缓存是否命中。
- 检索异常。
- 权限变更时间。

禁止在普通业务日志中直接打印敏感文档全文。

发现未授权 Chunk 时，必须阻断模型上下文构建，并产生安全告警。

## 十一、专项测试要求

必须补充自动化测试，至少包含以下场景：

1. 单角色授权一个知识库。
2. 多角色授权多个知识库，验证并集。
3. 没有角色授权。
4. 用户拥有角色，但角色没有知识库授权。
5. 父目录授权，子目录继承。
6. 同一知识库中部分目录授权、部分目录未授权。
7. 用户被撤销知识库权限。
8. 文档移动到未授权目录。
9. 文档删除或失效。
10. 同一智能体不同用户拥有不同知识库权限。
11. 同一个用户同时打开多个对话。
12. 超级管理员访问全部允许范围。
13. 普通用户不能通过修改请求参数访问其他知识库。
14. 向量检索和关键词检索同时执行权限过滤。
15. 检索缓存不能跨授权范围复用。
16. 历史对话中的旧知识引用不能绕过权限校验。
17. 子 Agent 和工作流不能绕过权限过滤。
18. 授权范围为空时绝不执行无过滤全库检索。
19. 向量数据库过滤异常时不能降级成全库检索。
20. 未授权知识库中存在更高相似度内容时，不得影响授权知识库正常回答。

特别增加一个回归测试：

假设用户只有 K1 权限，K2 中存在比 K1 更相似的文档。

预期结果：

- 只检索 K1。
- 不比较 K1 与 K2 的向量距离。
- 不因 K2 的存在而拒绝回答。
- K1 有相关内容时正常回答。
- K1 没有相关内容时正常返回无相关资料。
- K2 内容绝不能进入模型上下文。

## 十二、改造实施要求

请按以下顺序执行：

### 第一阶段：代码审计

先阅读：

- app.py 中 get_user_resource_scope()
- app.py 中 chat()
- chat() 中知识库检索与距离比较逻辑
- 向量数据库封装
- 目录与文档数据模型
- RAG 缓存
- Agent 工具与工作流的知识库调用入口

输出当前权限调用链、实际数据结构、潜在越权点和改造清单。

### 第二阶段：核心权限检索改造

优先完成：

1. 保留现有 RBAC 角色授权并集。
2. 保留超级管理员逻辑。
3. 实现授权目录范围计算。
4. 将授权过滤前置到检索阶段。
5. 移除全库召回后的最佳距离比较。
6. 实现检索结果二次权限校验。
7. 区分无权限、无相关资料和检索异常。

### 第三阶段：缓存与上下文安全

处理：

- 检索缓存隔离。
- 对话历史权限校验。
- 历史引用重新授权。
- Agent 工具调用权限。
- 子 Agent 和工作流权限。

### 第四阶段：自动化测试与回归

完成上述测试场景，确保没有权限的知识内容不能进入模型上下文。

## 十三、代码改造约束

1. 先分析现有项目，不要凭空假设数据库字段。
2. 优先复用已有角色、目录、知识库和文档模型。
3. 不要无理由新增数据库表。
4. 不要改变现有智能体问答业务流程。
5. 不要破坏超级管理员现有功能。
6. 不要破坏多角色授权并集逻辑。
7. 不要影响现有 HTTP 工具、附件和通用问答功能。
8. 不要为了权限过滤而重新生成全部 Embedding。
9. 不允许权限异常时自动回退到全库检索。
10. 所有权限判断必须在服务端完成。
11. 保证现有 API 兼容性。
12. 每个阶段完成后运行相关测试。

如果发现当前向量数据库或检索框架无法支持所需的过滤能力，先分析并提出兼容当前架构的实现方案，不要直接更换技术栈。

## 十四、最终交付

改造完成后输出：

1. 当前权限问题根因分析。
2. 改造前后的检索链路对比。
3. 修改文件清单。
4. 核心权限过滤实现。
5. 缓存与历史上下文隔离实现。
6. 自动化测试结果。
7. 尚未解决的风险点。

最终验收标准：

**任何普通用户的知识库检索，都只能在其当前角色授权范围内进行。未授权知识库不参与召回、不参与排序、不参与模型上下文构建，也不能通过缓存、历史对话、工具调用或工作流绕过权限控制。**

权限控制必须是确定性的服务端安全边界，而不是依靠向量相似度或大模型判断。
